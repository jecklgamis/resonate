### What this is

`resonate` is a Go CLI load generator (HTTP, WebSocket, gRPC and Server-Sent Events), currently beta (the YAML schema, `report.json`/`results.jsonl` fields and exit codes are a stable contract — see `docs/reports.md#stability`; `internal/cli/contract_test.go` guards it). Two entry points: `resonate hit <url>` for one-off flag-driven HTTP runs, and `resonate run <scenario.yaml>` for reusable, multi-target/multi-step/WebSocket scenarios (`resonate hit` is HTTP-only; WS, gRPC and SSE are scenario-file only). The module path is `github.com/jecklgamis/resonate` (renamed from a bare `resonate`), and the same engine is also importable as a library via the root `resonate` package — see `docs/library.md` and `resonate_test.go`. `docs/cli/*.md` is a generated, always-in-sync flag reference (`make docs`/`make docs-check`); don't hand-edit it. The rest of `docs/` (`README.md`, `install.md`, `usage.md`, `scenarios.md`, `grpc.md`, `sse.md`, `http3.md`, `execution-models.md`, `reports.md`, `library.md`, `architecture.md`, `index.html`, `_sidebar.md`) is a hand-written docsify site, published via GitHub Pages at https://jecklgamis.github.io/resonate/ (branch-deploy of `main`/`docs`, no build step) — also browsable as plain Markdown on GitHub or via `docsify serve docs` locally. It's the source of truth for user-facing behavior (flags, YAML schema, templating functions, execution models) — keep it current, and don't duplicate its content elsewhere. The root `README.md` is deliberately a short overview (install one-liner, quick start, links) that points into `docs/` for everything else — don't grow it back into a full reference; add detail to the relevant `docs/*.md` page instead. CONTRIBUTING.md covers the PR/issue workflow.

### Commands

```sh

make test           # go test ./...
make check          # fmt-check + vet + test (run this before considering work done)
make fmt            # gofmt -w .
make example-grpc-server  # demo gRPC server (examples/testgrpcserver, :50051) that examples/grpc-*.yaml target; ARGS=-reflection=false turns reflection off
make example-sse-server   # demo SSE server (examples/testsseserver, :8765) that examples/sse-*.yaml target
make example-http3-server # demo HTTP/3 server (examples/testhttp3server, :8443 UDP+TCP) that examples/*-http3.yaml target; ARGS=-h3-only drops TCP
make docs           # regenerate docs/cli/*.md from the cobra command tree (cmd/gendocs)

go run ./cmd/resonate compare baseline.json report.json --fail-on 'latency_p95>10%'   # regression gate between two JSON reports
go test ./... -race # always run -race when touching internal/engine or internal/generator — both use goroutines/atomics/sync.Map
go test ./internal/engine/... -run TestScheduleAtRampsLinearly -v   # single test
go run ./cmd/resonate hit http://localhost:8080/health --duration 5s   # run without building a binary
```

No linter beyond `go vet`/`gofmt` is configured. `go.mod` pins `go 1.27.1`. CI (`.github/workflows/ci.yml`) runs `make check` plus `make docs-check` on every push/PR to `main`; `.github/workflows/release.yml` cross-builds and publishes a GitHub release on any `v*` tag push.

### Architecture

**Request flow:** `cli` parses flags/YAML → builds a `generator.Generator` (`HTTPGenerator` or `FlowGenerator`) → hands it to `engine.Run` → `engine` drives the generator at the configured concurrency/rate, streaming `generator.Result`s into a `report.Aggregator` → `report.Summary` is printed (text or `--json`).

- **root package (`resonate`, files `doc.go`/`generator.go`/`engine.go`/`report.go`)** — the public, embeddable API; everything in it is a type alias (`type Foo = generator.Foo`) or a one-line wrapper function around `internal/generator`/`internal/engine`/`internal/report`, so values stay fully interchangeable with code that imports those internal packages directly (e.g. `internal/cli`) — no conversion layer, no duplicated logic. `internal/cli` (Cobra) and `internal/tmpl` are deliberately *not* promoted — a library consumer builds `HTTPTarget`/`FlowStep`/`WSMessage` values in Go directly rather than going through flag parsing or YAML. Adding a new exported type/func to `internal/generator`/`engine`/`report` does **not** automatically make it public — it has to be added here explicitly, which is the intended friction (keeps the public surface deliberate, not "whatever happens to be exported internally today"). `report.go`'s `WriteHTMLFile(path, HTMLReport)` is the one function that isn't a pure passthrough — it does the `os.Create`/`defer Close()`/`WriteHTML` dance that `internal/cli/common.go`'s private `writeHTMLReport` also does, just exposed publicly instead of duplicated per-caller.
  - `dsl.go`'s `Scenario` is a fluent builder over that same facade (chained setters accumulate into unexported `[]HTTPTarget`/`[]FlowStep`/`HTTPOptions`/`Options`, `Build()`/`Run()` call the existing `NewHTTPGenerator`/`NewFlowGenerator`/`NewWSGenerator`/`Run`) — purely additive sugar, not a parallel implementation; covers every protocol — HTTP (`Target`), flow (`Step`/`Setup`), WebSocket (`WS`/`Message`), SSE (`SSE`) and gRPC (`GRPC`/`Call`), the last two in `dsl_protocols.go`. `Method`/`Get`/`Post`/.../`Header`/`Query`/`Body`/`Expect*`/`Pause` all mutate "whichever request is currently being built" through a `*stepRef` (a struct of field pointers into either the last `HTTPTarget` or the last `FlowStep`, set by `targetRef`/`flowStepRef`) rather than duplicating those setters per underlying type; `ensureCurrent` lazily starts a step on first use — in a live flow (`s.active != nil`) it appends to whatever list is currently active, otherwise it falls back to the implicit single `HTTPTarget`, so the common case needs no `Target`/`Step` call at all. `Target(method,url)` appends an additional independent target (round-robin `HTTPGenerator`, like YAML's `targets:`); `Step`/`Setup(method,url)` append to the flow/setup slice instead (like YAML's `flow:`/`setup:`) and switch `Build()` to construct a `FlowGenerator`; `Extract`/`Identity`/`Pause`/`PauseRange` are flow-only (each a no-op if the corresponding `stepRef` field is nil, i.e. current is a plain `HTTPTarget`). `Repeat(n)`/`During(d)`/`If(cond)` open a control-flow block via `openBlock` (append a control `FlowStep` to `*s.active`, push the old `s.active` onto `s.stack`, repoint `s.active` at the new block's `.Steps`); `End()` pops `s.stack` back to the enclosing list. `s.active`/`s.stack` hold pointers to slice *fields* (`&s.flow`, `&s.setup`, or `&someBlock.Steps`), never to a raw slice element, specifically so a later `append` that reallocates a slice's backing array can't leave a stale pointer live in `s.stack` — see the `openBlock`/`stepRef` doc comments before changing this. `Target` and `Step`/`Setup` are mutually exclusive — `Build()` rejects a `Scenario` with both `s.targets` and `s.flow`/`s.setup` non-empty rather than silently picking one (same fail-fast philosophy as the rest of construction-time validation). `FileBody(path)`/`RawFileBody(path)` are the only two `Scenario` methods that do I/O that can fail (`os.ReadFile`) — rather than change their signature to return `(*Scenario, error)` and break the fluent chain, a failure calls `s.deferErr(err)` (keeps the *first* error only) and `Build()` checks `s.buildErr` before anything else, so a bad path surfaces at `Build()`/`Run()` like every other `Scenario` validation error. `RawBody`/`RawFileBody` set `stepRef.rawBody` (unlike `extract`/`pause`, this pointer is valid on *both* an `HTTPTarget`- and `FlowStep`-backed ref, since a raw body is meaningful on an independent `Target` too, not just flow steps) — mutual exclusion with `Body`/`FileBody` is enforced downstream by `compileHTTPFields`, not re-checked in `dsl.go`. Covers all four execution models via `Rate`/`Workers`/`MaxWorkers`/`Duration`/`Requests` (flat closed/open) plus `Stages`/`Iterations` (ramped/VU-lifetime-bounded) — when adding a new `Options` field, add the matching `Scenario` setter too, or it becomes silently unreachable through the DSL (all backing fields are unexported, so there's no struct-literal escape hatch once you're using `Scenario`). `BaseURL(url)` just sets `s.httpOpts.BaseURL` — the actual `/`-prefix resolution happens once, downstream, in `compileHTTPFields` (see below), shared by every surface (DSL, struct-literal `HTTPOptions`, scenario YAML) rather than duplicated per caller. `Feeder(path, mode)` calls `NewFeeder` immediately (deferring a load error via `deferErr`, same pattern as `FileBody`/`RawFileBody`) and sets `s.httpOpts.Feeder` or, once `WS` has been called, `s.wsOpts.Feeder`. `Assert(...Assertion)` appends to `s.assertions`; `Run` evaluates them via `Summary.Evaluate` after the run and folds any failures into one joined error (`Failure.String()` per line) rather than changing `Run`'s `(Summary, error)` signature — the `Summary` is still returned even when assertions fail, mirroring `resonate run`/`resonate hit` printing the report before exiting non-zero. **`dsl_protocols.go` is the rest of the builder's surface, and the rule it follows is parity: anything a protocol's YAML or struct API can express must be reachable from `Scenario`, and a setter that can't apply to the scenario's protocol is a `Build()` error rather than ignored.** The exceptions are old, documented no-ops that were left alone to avoid changing existing behaviour: `Extract`/`Pause`/`PauseRange`/`Identity` on a plain `Target` (only flow steps use them), `Extract`/`Pause`/`PauseRange` on SSE, and `BaseURL` on WS/gRPC. `docs/library.md`'s "Which methods apply to which protocol" table is the reference for all of this and was generated from a probe that applies every setter to a minimal scenario of each protocol (flow vs plain target separately) — redo that probe if a setter is added or its applicability changes, since a table of ✓/— cells drifts silently. A `Scenario` is exactly one protocol (`checkModes` at `Build()`: HTTP via `targets`/`flow`/`setup`, or `ws`/`sse`/`grpc`; a stray `Get`/`Header` on a WS/gRPC scenario starts an implicit HTTP target and trips the same check). `SSE(method, url)` mirrors `Target`/`Step` (not `WS(url)`, since SSE can be a POST): it points `s.cur` at a `stepRef` over the `SSETarget` (`sseRef`), so `Method`/`Header`/`Query`/`Body`/`RawBody` describe the stream's request with no duplicated setters — which means `Get(url)` after `SSE(...)` *retargets the stream*, it doesn't add a second target; the `stepRef` fields SSE lacks (`name`, `expect*`) are nil, so `Name`/`ExpectStatus`/`ExpectHeader`/`ExpectBody` guard on nil and `deferErr` instead of dereferencing it (a panic before the guard existed). SSE is HTTP underneath, so it shares `httpOpts` (and its feeder) with the HTTP modes. `GRPC(address)` + `Call(method)` follow the `curMsg` pattern with `curCall` repointed on every `Call`; `Message` on a gRPC scenario *sets* the call's one request (a second is an error — `Messages(...)` is the client-stream form) while on WS it *appends* a frame; `Metadata(k,v)` is scenario-level before any `Call` and call-level after one (the gRPC analogue of `Header` before the first `Message` on WS); `Header` on gRPC is rejected ("use Metadata"). Names that collide with existing builder methods got distinct spellings rather than overloading: `SendRepeat` (not `Repeat`, the flow block), `StreamDuration` (not `Duration`, the load duration; it sets the SSE stream's or the current gRPC call's), `Events` (SSE) vs `Receive` (gRPC). The HTTP transport setters the first builder lacked (`FollowRedirects`, `MaxIdleConns`, `MaxResponseBody`, `H2C`, `DisableKeepAlive`, `CAFile`, `ClientCert`) record themselves in `s.httpOnly` and `checkHTTPOnly` rejects them on a WS/gRPC scenario **at `Build()`, not in the setter**, because `H2C().WS(url)` is as legal a call order as `WS(url).H2C()` and a setter can't know yet; `CAFile`/`ClientCert` instead route to `grpcOpts` for gRPC and error for WS (which has no CA/cert options). `setFeeder` is the one place `Feeder`/`FeederRows` pick `grpcOpts`/`wsOpts`/`httpOpts`. `Message`/`Wait`/`Binary` outside WS (or before the first `Message`) used to be silent no-ops and are now errors, for the same fail-fast reason as the rest of construction-time validation. Tests (`dsl_protocols_test.go`) were mutation-checked option by option and that found real holes: a gRPC `Timeout`/feeder/`Metadata` scope/`StreamDuration` test that passed with the option dropped (the health service reports an empty service name as SERVING, so a missing feeder row looked fine; an SSE server that closes by itself made `Events` and `StreamDuration` unobservable). Options with no black-box signal in a unit test are proven by the generator *rejecting* them (a streaming-only field on the unary `Health/Check` call: `Messages`/`SendRepeat`/`SendInterval`/`Receive`; a nonexistent `CAFile`/`ProtoFiles` path) or, for `MaxIdleConns` (idle-pool behaviour is goroutine-timing dependent), by a white-box check in `dsl_internal_test.go`. `Run` also validates step-scoped assertions against the built generator's `StepNames()` (`ValidateSteps`), hands every assertion with `Abort` set to the engine as `Options.AbortOn` (after `ValidateAbort`), and returns the partial `Summary` plus an `aborted` error if the engine stopped it; `Name(label)` sets `stepRef.name` (an error after `WS`, which has no per-step breakdown). `WS(url)` sets `s.ws`/`s.wsOpts` (mutually exclusive with `Target`/`Step`/`Setup`, checked in `Build()`); `Message(body)` appends a `WSMessage` to `s.ws.Messages` and repoints `s.curMsg` at it, the WS analogue of `stepRef`/`ensureCurrent` — `Wait`/`Binary`/`Extract`/`ExpectBody` mutate `s.curMsg` directly (no `stepRef` involved, since `WSMessage`'s field set doesn't overlap enough with `HTTPTarget`/`FlowStep` to share one) and `Header`/`Timeout`/`Insecure` branch on `s.ws != nil` to target `s.ws.Header`/`s.wsOpts` instead of the HTTP path; `BaseURL` is a no-op once `s.ws != nil` (`WSOptions` has no `BaseURL`). `Build()` also rejects a WS message with `Extract`/`ExpectBody` set but no `Wait` (mirroring `internal/cli/run.go`'s `buildWSGenerator` check, which `internal/generator.NewWSGenerator` itself does not enforce) since the DSL has no other fail-fast validation pass before construction.
- **`internal/generator`** — the `Generator` interface: `Do(ctx, vuID) []Result`. One call is one "iteration" — a single HTTP call for `HTTPGenerator` (independent, round-robin `targets`), every step in an ordered sequence for `FlowGenerator` (`flow`, chaining `{{.Vars.*}}` extracted from earlier responses, optional `setup` run once per VU, optional `identities` pool), or connect+send/receive a message sequence for `WSGenerator` (`ws.go` — deliberately dials fresh every iteration rather than pooling a connection per VU, since the `Generator` interface has no "this VU has departed for good" hook to close a pooled connection without leaking sockets during `Iterations`-driven VU churn). `compileHTTPFields`/`doHTTP` (`http.go`) are shared by `HTTPGenerator` and `FlowGenerator`; `WSGenerator` reuses `extractValue` (`extract.go`) for its own chaining but not `httpFields`. `vuID` is a *virtual user* identity, not necessarily tied 1:1 to a goroutine — see engine below.
  - `flow.go`'s `FlowStep` is either a request or a control-flow block (exactly one of `Repeat`/`During`/`If` set, plus `Steps`) — never both; `compileStep` validates that mutual exclusivity and that a control step has ≥1 nested step, at construction. `compileSteps`/`compileStep` are mutually recursive so `Steps` nests arbitrarily deep. Execution is `runSteps(ctx, client, steps, data, vars, maxBody, &results)`, called once per `Do()`/`setupVarsFor` instead of the old flat `for range a.flow` loop — it recurses into `controlRepeat`/`controlDuring`/`controlIf` blocks and returns `false` the moment a request step fails (`Error != nil || !Success()`) or `ctx` is done, which every recursion level propagates immediately (`if !runSteps(...) { return false }`) so one failed request unwinds out of *every* enclosing block, stopping the whole flow — not just the innermost loop. `data.Vars` aliases the same `vars` map for the whole recursive call tree (maps are reference types), so extracted values from one step are visible to a later `If`'s condition or a later step without rebuilding `tmpl.Data`. `Pause`/`PauseMax` sleep via `sleepCtx` (a `time.Timer` racing `ctx.Done()`, so a cancelled/expired run doesn't block on a long pause) immediately before a request step's `doHTTP` call; `pauseDuration` returns a fixed `Pause`, or (if `PauseMax > Pause`) a uniform random draw via `math/rand/v2`. `setupVarsFor` now also runs through `runSteps`, so setup steps get the same stop-on-failure/pause/control-flow behavior as flow steps (previously setup had its own flat loop that never stopped early on failure — that inconsistency is gone).
  - `HTTPTarget`/`FlowStep.RawBody []byte` sends the body exactly as given, entirely bypassing `tmpl` — for a large/binary payload or one that would otherwise be misread as containing `"{{ }}"` syntax. `compileHTTPFields` rejects `body != "" && rawBody != nil` at construction (mutually exclusive); `nil` means "unset" and falls through to the normal templated `Body`/`tmpl.Field` path, while a non-nil *empty* slice (`[]byte{}`) is a deliberate empty body — `doHTTP` distinguishes the two paths with `f.rawBody != nil`, computing `bodyLen`/`bodyReader` once up front (from `len(f.rawBody)`/`bytes.NewReader` or from rendering `f.body`) so `BytesOut` and the `http.NewRequestWithContext` body arg share one code path afterward regardless of which source was used. CLI/YAML resolve `--raw-body-file`/`raw_body_file` to bytes ahead of construction (`internal/cli/hit.go`, `internal/cli/run.go`'s `resolveBody`) — if both a templated and a raw body source are given, the CLI layer warns and the raw one wins (never lets both reach `compileHTTPFields` at once from that path); the construction-time error only fires from direct Go API/DSL use (`HTTPTarget{Body: "x", RawBody: []byte("y")}`, or `Scenario.Body(...).RawBody(...)`).
  - `httpFields.expectStatus`/`expectHeaders`/`expectBody` (from `HTTPTarget`/`FlowStep`'s same-named fields, validated at `compileHTTPFields` construction — status codes as 100-599, header names as non-blank, body rules via `isKnownExtractRule`) are a per-target override of the default 2xx/3xx success range, combined with AND when more than one is set. `doHTTP` sets `Result.successOverride` (a `*bool`, nil everywhere else — including every `Result{...}` literal in the test suite and `ws.go`'s synthetic connect results — so `Success()` falls back to the original `Error == nil && 2xx/3xx` check unless a target actually configured one of these) rather than just setting `Error` on mismatch, because `Success()`'s hardcoded range check can't otherwise be talked into accepting e.g. an expected 404 as a success. `expectHeaders` matching is via `resp.Header.Get` (case-insensitive name); an empty expected value only checks presence (`resp.Header.Values(name)` non-empty) rather than an exact match. `expectBody` reuses `extractValue` (below) keyed by rule (`json:`/`yaml:`/`xml:`/`header:`/`status`) — buffering the body (`if len(extract) > 0 || len(f.expectBody) > 0`) the same way `extract` already does; an empty expected value only requires the rule to evaluate without error. On any mismatch `doHTTP` also sets `Error` with all the failed check(s)' reasons joined (sorted names for determinism), both for the report's `Errors` breakdown and because `FlowGenerator.Do` already stops a flow's remaining steps on `!Success()`. `ws.go`'s `WSMessage.ExpectBody` is the same mechanism applied to one message's response frame (only meaningful alongside `Wait: true`, enforced in `cli.buildWSGenerator`), also breaking the message sequence on failure.
  - **Step names** (`Result.Step`, `HTTPTarget.Name`/`FlowStep.Name`): every HTTP `Result` — including transport errors and request-build errors, both of which `doHTTP` returns early on, so each of its three `Result{...}` literals sets it — carries the label of the target/flow step that made it, which is what lets `report.Aggregator` break a run down per step. `stepName(name, f)` is the label: the configured name, else `"METHOD url"` built from `httpFields.rawURL` (the template *source*, so `GET /u/{{.Vars.id}}` is one step rather than one per user) with `?`/`#` and `user:pw@` cut off, so a label can never carry a secret into a report (`TestStepNameNeverCarriesCredentialsOrQuery`). It is set on `httpFields.name` *after* `compileHTTPFields` rather than via a new parameter, since SSE and tests call that with a long positional signature. Requests that share a label merge into one step (also how a repeated step in a `repeat` block is reported). A `repeat`/`during`/`if` block can't be named (`compileStep` rejects it) — name the requests inside. `HTTPGenerator`/`FlowGenerator.StepNames()` list the labels (setup steps excluded: their results are discarded, so an assertion on one could never pass) and are found by `cli`/`dsl` through an anonymous `interface{ StepNames() []string }` assertion, so WS/gRPC/SSE simply don't have it — they have no per-step breakdown, and a step-scoped assertion on them is rejected at construction.
  - `extract.go`'s `extractValue` (`json:<JSONPath>`, `yaml:<JSONPath>`, `xml:<XPath>`, `regex:<pattern>`, `css:<selector>`, `header:<Name>`, `status`) is real JSONPath (`github.com/ohler55/ojg/jp`), XPath 1.0 (`github.com/antchfx/xmlquery`, backed by `github.com/antchfx/xpath`), the stdlib `regexp` package (RE2, so no backreferences/lookaround), and CSS selectors (`github.com/PuerkitoBio/goquery`, backed by `github.com/andybalholm/cascadia`) — not the hand-rolled dot-path traversal it started as. `jsonPath(v any, expr string)` takes an already-decoded value and prepends `"$."` (or just `"$"` if the expr already starts with `"["`) when the caller's expr has no leading `"$"`, so `json:id` and `json:$.id` are equivalent — but this means the old `json:items.0.id` dot-index shorthand no longer resolves; real JSONPath bracket syntax (`json:items[0].id`) is required now. `yaml:` rules `yaml.Unmarshal` the body (`gopkg.in/yaml.v3`, already a direct dependency via `internal/config`) into the same `any` shape and reuse the identical `jsonPath` call — verified empirically that `ojg/jp` handles yaml.v3's native Go types (`int`, not just JSON's `float64`) without issue. `xmlPath` passes the expr straight to `xmlquery.Query` with no rewriting, so it must be a real (relative or absolute) XPath expression; `node.InnerText()` correctly returns the value for both element and attribute-node matches (verified empirically — `antchfx/xmlquery`'s doc comments don't spell this out). `regexMatch` returns the first capturing group if the pattern has one, else the whole match — `FindSubmatch` against the raw `[]byte` body, no JSON/XML/HTML parsing involved. `cssSelect` parses the body as HTML (`goquery.NewDocumentFromReader`, tolerant like a browser — doesn't error on non-HTML the way `xmlPath`'s strict XML parse does) and returns the first matching element's trimmed `.Text()`.
  - `newHTTPClient(HTTPOptions) (*http.Client, error)` builds **one** `*http.Client`/`*http.Transport` for the whole generator — shared by every worker goroutine for the entire run, not one per VU (a VU/`vuID` has no connection identity at all, it's purely logical: `{{.VU}}` templating, sticky `Identity`/setup vars). Actual connection pooling is 100% delegated to Go's stdlib `net/http.Transport`: `MaxConnsPerHost` is never set (default 0 = unlimited), so concurrent requests can always open as many simultaneous connections as needed; `MaxIdleConnsPerHost` (`--max-idle-conns`/`http.max_idle_conns`, default 100) only bounds how many stay open *idle* for reuse after a request completes — anything beyond that gets torn down and re-dialed next time instead of reused. This is a real, measured footgun once `MaxWorkers` is pushed past the idle-conn default: at 1000 concurrent with only 100 idle conns kept warm, most connections get re-established per request (fresh TCP+TLS handshake), which shows up as inflated p95/p99/max latency and a real throughput shortfall that has nothing to do with the target server — confirmed empirically (10k rps run: 7.3k/s achieved + p99 1.46s at `--max-idle-conns 100`, vs. 10.4k/s achieved + p99 736ms at `--max-idle-conns 1000`, identical everything else). See README's "Connection reuse at high concurrency" section. `newHTTPClient` now returns an error (bad cert/key/CA file, or an invalid option combination) so `NewHTTPGenerator`/`NewFlowGenerator` fail at construction rather than per-request. `HTTPOptions` covers `MaxResponseBody` (caps response bytes read/counted per request — `doHTTP` still drains-and-discards the remainder via `io.Copy(io.Discard, resp.Body)` so the connection stays reusable even when capped), `CertFile`/`KeyFile` (mTLS), `CAFile` (trust a private CA), `H2C` (prior-knowledge HTTP/2 over plaintext via `golang.org/x/net/http2`, with a custom `DialTLSContext` dialing plain TCP — Go's stdlib `Transport` only negotiates HTTP/2 via TLS ALPN), and `DisableKeepAlive` (maps to `Transport.DisableKeepAlives`). `H2C` is mutually exclusive with `Insecure`/`CertFile`/`KeyFile`/`CAFile`/`DisableKeepAlive` — all TLS-only or persistent-connection concerns that HTTP/2's `http2.Transport` has no equivalent knob for, so combining them is rejected at construction instead of silently no-opping (same validation philosophy as below).
  - `feeder.go`'s `Feeder` hands out one row per `Next()` call, from `NewFeeder(path, mode)` — round-robin via an atomic counter in `"sequential"` mode (the default), `math/rand/v2` in `"random"` mode, or (see below) a background-goroutine reader in `"stream"` mode. Threaded through `HTTPOptions.Feeder` (read by both `HTTPGenerator` and, via `FlowOptions.HTTP`, `FlowGenerator`) and `WSOptions.Feeder`; exposed to templates as `{{.Feeder.<column>}}` via a new `tmpl.Data.Feeder` field alongside `Identity`/`Vars`. `FlowGenerator.Do` picks one row per iteration (before the step loop) so every step in that flow sees the same row, mirroring how `Identity` is sticky rather than re-picked per step; `setupVarsFor` picks its own row once per VU. `Feeder.Next()` is nil-receiver-safe (`(*Feeder)(nil).Next()` returns `nil`) so callers don't need an `if opts.Feeder != nil` check at every call site.
    - `NewArrayFeeder(rows, mode)` builds a `Feeder` from rows already in memory (Gatling-style array feeder) — same `rows`/`random`/`counter` fields as the file-backed modes, so `Next()` is unchanged. It copies `rows`, accepts only `"sequential"`/`"random"` (`"stream"` is file-only and rejected), and fails on empty input. YAML reaches it via `config.FeederConfig.Rows` → `cli.newFeeder` (mutually exclusive with `file`/`kafka`; `Configured()` counts it as a source); the DSL via `Scenario.FeederRows`; `scenario.schema.json`'s `feeder.oneOf` must be kept in step with any new source. No `queue`/`shuffle` modes yet.
    - `"sequential"`/`"random"` load the whole file into `[]map[string]string` once at construction (`loadCSVFeeder`/`loadJSONFeeder`) — simplest, but a real problem for a file too large to comfortably fit in memory (Go maps have significant per-entry overhead beyond the raw data, so a 10GB file can realistically need 30-100GB+ RSS this way; measured ~40x file-to-RSS blowup on a 36MB/2M-row CSV in practice).
    - `"stream"` mode (`streamFeeder`) fixes that: a background goroutine reads one row at a time via `rowSource` (a thin CSV/JSON incremental reader — `csv.Reader.Read()` already reads one record at a time; JSON uses `json.Decoder.Token()`/`More()`/`Decode()` to walk the array without `json.Unmarshal`-ing it whole) and feeds a small buffered channel (`streamFeederBufferSize`, currently 1000 rows) that `Next()` just receives from — memory stays bounded to that buffer regardless of file size. On EOF it closes and reopens the file from scratch (`openWithRetry`, with `streamReopenBackoff` between attempts) rather than trying to `Seek` an already-buffered reader back to 0, which wraps around indefinitely the same way `"sequential"` does, and also self-heals if the file is briefly unavailable.
    - `streamFeeder`/`Feeder.Close()` exist *only* because `"stream"` mode has a goroutine + open file handle to release — `"sequential"`/`"random"` `Feeder`s have nothing to close, so `Close()` on those is a no-op. `Close()` is wired into `HTTPGenerator`/`FlowGenerator`/`WSGenerator.Close()` (`a.feeder.Close()`, nil-safe). Correctness here depends on `Close()` only being called after nothing can still call `Next()`, since a `Next()` racing a `close(sf.stop)` could otherwise block forever on the now-abandoned channel — that precondition holds structurally in this codebase because every `Generator.Close()` call site only runs after `engine.Run` has returned, and `Run` doesn't return until every worker goroutine (the only `Next()` callers) has already stopped; don't call `Feeder.Close()` from anywhere that isn't already past that point.
    - `NewFeeder`'s fail-fast contract (bad file/empty dataset errors at construction, before any request is sent) applies to `"stream"` mode too — `newStreamFeeder` opens a throwaway `rowSource`, scans every row to confirm the file is well-formed and non-empty, then closes it; the background goroutine then opens its own fresh `rowSource` from scratch rather than reusing that one.
    - `kafka_feeder.go`'s `NewKafkaFeeder(KafkaFeederOptions)` returns the *same* `*Feeder` (a `kafka *kafkaFeeder` field next to `stream`), so every protocol gets it with no per-generator change; scenario YAML reaches it via `feeder.kafka` → `cli.newFeeder` (the one place all four `buildXGenerator` feeder sites go through; also rejects `file`+`kafka`, `mode`+`kafka`, `password`+`password_env`).   - `grpc.go`/`grpc_stream.go`/`grpc_schema.go`'s `GRPCGenerator` makes gRPC calls of every kind — unary, server-, client- and bidirectional-streaming; the kind is read from the method descriptor (`grpcKind`), never declared in config, and `bindGRPCCall` rejects fields that don't suit it (`receive` on a unary call, `message` on a client-streaming one, ...) at construction. `GRPCTarget{Address, Metadata, Calls []GRPCCall}` mirrors `WSTarget`'s shape: calls run in order each iteration, `Extract` feeds `{{.Vars.*}}`, and the first failed call ends the iteration (like `FlowGenerator`/`WSGenerator`). No codegen: messages are `dynamicpb.Message`s, the request JSON (templated via `tmpl`) goes in through `protojson.Unmarshal`, and the response comes back out through `protojson` with `EmitUnpopulated: true` (so `json:count` finds a zero-valued field) and is fed to the shared `extractValue`/`isKnownExtractRule` — `header:` rules read response headers+trailers merged into an `http.Header`, and `status` is the gRPC code *number*. A call whose message has no `{{` is parsed once at construction (fail-fast on typos) into `compiledGRPCCall.static`, which is then shared read-only across goroutines (covered by a `-race` test). **Schema source** (`descriptorResolver`, satisfied by both `*protoregistry.Files` and protocompile's `linker.Resolver`): `ProtoFiles` (`bufbuild/protocompile`, `ImportPaths` defaulting to the files' own directories) > `DescriptorSet` (`protodesc.NewFiles`, which accepts files in any order) > server reflection. Reflection is a hand-rolled bidi-stream client (`reflectOnce`) over `grpc_reflection_v1`'s message types, tried against both the `v1` and `v1alpha` method paths — the two are wire-identical, so one set of types serves both and only an `Unimplemented` status triggers the fallback; missing imports are chased with `FileByFilename`, preferring `protoregistry.GlobalFiles` for well-known types. This means **construction can do network I/O** (reflection only) and fails there if the server is unreachable or has reflection off, with an error naming the `proto_files`/`descriptor_set` alternatives. **Results**: `Protocol: "grpc"`, `StatusCode` is the gRPC code mapped to its HTTP equivalent (`httpStatusFromGRPCCode`; OK→200, NOT_FOUND→404, ...) because `Result.Success()` and the report's status breakdown are HTTP-shaped (same synthetic-200 precedent as `ws.go`) — the real code lives in `Result.Error` (`rpc error: code = ...`) and in `ExpectCode` mismatch messages; `ExpectCode`/`ExpectBody` set `successOverride` exactly like `doHTTP`'s `expect_*`, and `ExpectBody` alone still requires `OK`. `BytesIn`/`BytesOut` are `proto.Size` of the messages. **Wait-for-ready is deliberate**: every call passes `grpc.WaitForReady(true)`, because a fail-fast RPC against a down server returns `Unavailable` in microseconds and a worker with no `--rate` would spin at millions of calls/sec — the same free-spin hazard `validateLiteralURL` exists for; `TestGRPCGeneratorDownServerWaitsForTimeoutInsteadOfSpinning` was verified to fail (14µs calls) with the option removed. **Connections**: `GRPCOptions.Connections` (default 1) dials that many `*grpc.ClientConn`s via the non-blocking `grpc.NewClient` and VU `i` uses `conns[i % n]` — one conn is one HTTP/2 conn and servers typically cap ~100 concurrent streams on it, so past that calls queue *client-side* and inflate latency (the gRPC analogue of the `MaxIdleConnsPerHost` footgun above). TLS reuses `newTLSConfig` (extracted from `newHTTPClient` so both share one implementation); `Plaintext` is rejected alongside `Insecure`/`CAFile`/`CertFile`/`KeyFile`. Unary per-call timeout is `context.WithTimeout`; a unary call whose result is a failure while the run has ended (`runEnded(ctx)`: `ctx.Err() != nil` **or its deadline has passed**) is dropped in `Do` rather than reported. The deadline half matters: gRPC fails a call instantly when it sees `time.Until(deadline) <= 0`, but the context only marks itself done when its timer goroutine next runs a few µs later, so `ctx.Err()` alone missed it and every ramped run ended with a burst of ~one-per-worker 0ms `DeadlineExceeded` results (8–74 per run before the fix, 0 in 5 runs after; `lateCtx` in `grpc_stream_test.go` reproduces the window) — otherwise every run ends with a spurious `DEADLINE_EXCEEDED` that trips `success_rate` assertions (found load-testing a real server; `TestGRPCUnaryCallInterruptedByRunEndingIsNotAFailure`); there's no `hit` flag (a deliberate scope cut; the builder covers it — see `dsl_protocols.go` below).
  - **Streaming** (`invokeStream`): a stream is reported like a WebSocket connection, by its messages — one `Result` per *received* message (latency = gap since the previous one; the first: since the stream opened), plus one trailing failed `Result` if the stream failed in a way no message already shows, plus one success `Result` if it ended cleanly with zero messages (so it's still counted); total bytes sent are added to the first `Result`. Synthetic failures (ended early, timed out) use `StatusCode: 0` like an HTTP transport error; a server-ended failure uses the mapped status. A sender goroutine renders and `SendMsg`s `compiledGRPCCall.sends` (`repeat` times, `interval` apart) then `CloseSend`s, while the calling goroutine runs the `RecvMsg` loop — so sends never wait for replies. **The sender renders from a `maps.Clone` of `data.Vars`**, because the receive loop writes `extract`ed values into the real map; sharing it is a data race (`TestGRPCBidiExtractWhileSendingDoesNotRace` fails under `-race` without the clone, verified). End conditions: `receive` reached → cancel + success; `duration` (or `timeout` as a cap when it's unset) is a `time.AfterFunc` that sets a `limitHit` flag then cancels — own-timer expiry is told apart from a parent-`ctx` cancel (run ended: never a failure) by that flag, not by the error value; with neither `receive` nor `duration`, reaching the `timeout` cap is a *failure* (`capped`) so an endless stream can't pin a worker for the run, while `duration` alone elapsing is a success. `ExpectBody` applies to *every* received message (first mismatch fails and ends the stream); `Extract` runs on every message, last wins; `ExpectCode` is checked only against a status the *server* ended the stream with (a stream we cancel has none). `defer { cancel(); <-senderDone }` guarantees the sender never outlives the call (`...DoesNotLeak` test). Messages per stream accumulate in the returned slice, so unbounded high-rate streams cost memory — hence the cap-is-a-failure rule.
  - `HTTPOptions.HTTP3` (`--http3` / `http.http3` / `sse.http3` / the `Scenario.HTTP3()` builder method) swaps `newHTTPClient`'s `*http.Transport` for quic-go's `http3.Transport` (`rt http.RoundTripper`; the `http.Client`, redirect policy and TLS config — built by the shared `newTLSConfig` — are common to both paths). **Opt-in only**: no Alt-Svc discovery and no fallback, by design — a silent fall-back to TCP would make an HTTP/3 test measure HTTP/1.1, which is why the example server's `/proto` and the tests assert the *server-observed* protocol (`r.Proto == "HTTP/3.0"`), never just success.   - `sse.go`'s `SSEGenerator` (`SSETarget{Method,URL,Query,Header,Body,RawBody,Events,Duration}` + `SSEOptions{HTTP HTTPOptions, Identities}`, mirroring `FlowOptions`) reuses `compileHTTPFields` (no `expect_*`) and `buildRequest` — the request-building half of `doHTTP`, extracted so both share one implementation; `doHTTP` wraps its error into a `Result`. - **`internal/tmpl`** — wraps `text/template` for per-field `{{ }}` rendering (URL/query/header/body). Two things worth knowing before touching it: (1) fields with no `{{` skip templating entirely (`Compile` returns a literal-only `Field`) as a fast path — don't break that check when adding syntax; (2) the template is constructed with `Option("missingkey=zero")` so a never-extracted `{{.Vars.x}}` renders `""` instead of Go's default `<no value>` — this was a real bug once, don't remove the option. `Data.VU` carries the caller's `vuID` (set by every `Generator.Do`, including `HTTPGenerator`'s previously-ignored one) for `{{.VU}}`-based sharding. Funcs that can fail on bad input (`randDate`, `base64Decode`) return `(string, error)` — a template execution error propagates up through `Field.Render` and becomes a per-request `Result.Error`, not a panic; funcs that can't fail on any input (`randBool`, `padLeft`, `md5`, ...) just return the value.
- **`internal/engine`** — `Run` dispatches to `runFlat` (flat `duration`/`rate`/`workers`), `runOpenModel` (flat + `Rate>0` + `MaxWorkers>0`), or `runStaged` (`Stages`, a ramp schedule). See README's "Concurrency model" section (specifically "Execution models: open vs. closed") for the user-facing closed-vs-open-model explanation; this is the implementation side of it.
  - `runFlat` (closed model): a fixed pool of `Workers` goroutines ("slots"); an `x/time/rate.Limiter` paces iterations when `Rate>0`, but concurrency is still hard-capped at `Workers` — under latency, achieved throughput degrades toward `Workers/latency` instead of holding the target rate.
  - `runOpenModel` (constant-arrival-rate): a `rate.Limiter` paces iteration *starts* to `Rate` independent of latency; concurrency grows on demand via a dynamic pool of `MaxWorkers` "slots" (each holding one VU's identity/iteration-count state, only "occupied" by a goroutine while an iteration is in flight) instead of a fixed goroutine-per-slot design. If every slot is busy when a rate token mints, the iteration still runs once one frees up, but the run is flagged `report.Summary.Saturated` (with `PeakConcurrency`) rather than silently falling short.
  - `runStaged`: each stage is independently closed-model/ramping-vus (`Stage.Rate==0`: no pacing, concurrency ramps via `Stage.Workers`) or open-model/ramping-arrival-rate (`Stage.Rate>0`: paced, concurrency capped at `Stage.Workers` unless `Options.MaxWorkers` raises the ceiling past it, mirroring `runOpenModel`). **Does not** use `rate.Limiter`'s `SetLimitAt` for the ramp, on purpose — `Limiter.Wait()` commits to a delay computed from the rate *at call time* and won't speed up if the rate rises while already waiting, so an early low-rate `Wait()` call during ramp-up would resolve late and bunch up into a burst. Instead a ticker goroutine accumulates fractional "credit" from the *current* target rate each tick and mints tokens into a channel — see the comment block above `runStaged` before changing this. A stage's `Rate==0` case used to hang (workers blocked forever on a token the ticker never minted) — fixed by having a worker skip the token wait entirely when the *current* scheduled rate is 0, checked fresh each loop iteration since a schedule can mix `Rate==0` and `Rate>0` stages.
  - **VU lifecycle**: each goroutine slot starts as `vuID == slot`. If `Options.Iterations > 0`, once a VU hits its iteration cap it's replaced by a fresh VU via a *shared* atomic counter (`nextVU`), not `vuID += workerCount` — a per-slot stride would, whenever the identities pool size divides the worker count, land back on the same `identity % len(pool)` forever, defeating the point of rotating identities. If `Iterations` is the *only* stop condition (no `Duration`/`Requests`/`Stages`), `Run` computes an implied `Requests = Workers*Iterations` so the run is exact and self-terminating with no replenishment.
  - `ResolveWorkers`/`Validate` are exported because `cli` needs to reproduce/check the same worker-count logic the engine will actually use (for the concurrency-shortfall warning and for rejecting negative values) without duplicating it. `Validate` also enforces `MaxWorkers`'s constraints: requires `Rate>0` when `Stages` is unset (meaningless otherwise), and — flat only — `MaxWorkers >= Workers` when both are set; with `Stages`, `MaxWorkers` just raises the ramping ceiling and has no cross-field constraint.
  - **Abort on threshold** (`engine/abort.go`, `Options.AbortOn`): `Run` wraps `ctx` in a cancel and builds an `aborter` when `AbortOn` is non-empty; the three result loops (`runFlat`/`runOpenModel`/`runStaged`) used to be copy-pasted and are now one `collect(results, opts)` that calls `aborter.observe(agg, start)` after each `Add`. `observe` is throttled to `abortCheckInterval` (1s; a var so tests don't wait), skips assertions until their `AbortAfter` has elapsed, and evaluates `agg.Snapshot(elapsed)` — **not** `Summary()`, whose `bucketSeries` sorts every latency (O(n log n) per second on a long run); `Snapshot` is the headline numbers + per-step breakdown only. It uses `Summary.EvaluatePartial`, which *skips* a step-scoped assertion whose step hasn't produced a result yet (the final `Evaluate` fails it instead, since "no requests" at the end means it never ran). Once it trips it records `reason`, cancels the context, and `collect` keeps draining `results` but **discards everything after**: workers send with `select { results <- r; <-ctx.Done() }`, so in-flight requests cut off by the stop would otherwise leak in as `context canceled` errors (`TestAbortDiscardsResultsThatCompleteAfterTheStop` returns 50 late results per call because a ready select picks at random — one result would leak only ~50% of the time and let the filter be deleted unnoticed, which a mutation check caught). `Run` copies the reason into `Summary.Aborted`. It needs `requests > 0` (an empty run would fail every `success_rate`/`rate` at t=0), and `ValidateAbort` rejects `requests`/`success` (counts only mean something at the end), unknown metrics and a negative `AbortAfter`. The library default is `AbortAfter: 0`; the **CLI defaults `abort_after` to 5s** (`defaultAbortAfter` in `cli/run.go`) because the first requests' percentiles and success rate are too noisy to abort on. A single-stage `stages` schedule ramps from 0 workers, so nothing runs for a while — tests jump to the target with a zero-duration first stage.
- **`internal/report`** — `Aggregator.Add` per result, `.Summary(wallClock)` computes latency stats from an HDR histogram (`github.com/HdrHistogram/hdrhistogram-go`, 1ns–1h at 3 significant figures, so memory is fixed regardless of request count and percentiles carry ≤0.1% quantization error; latencies above 1h are clamped). `Aggregator` tracks exact `Min`/`Max` separately since the histogram only keeps 3 significant figures. `Summary.hist` (unexported, so it's invisible to `--json` output and to a library consumer building a `Summary` literal by hand) is the histogram kept alongside the precomputed `LatencyStats` so `Evaluate` can answer an *arbitrary* percentile assertion (`latency_p99.9`, not just the four fixed `LatencyStats.P50/P90/P95/P99` fields); `percentile(h, p)` is the shared helper. The `LatencyHistogram` bins are **log-spaced** (20 bins, geometric edges from `max(min, 1µs)` to `max`; equal-width bins crushed any long-tail run into the first bar) and built by assigning each HDR bar to the first bin whose upper edge is at or above its upper bound. Each `TimeBucket` also carries its own p50/p95/p99 (nearest rank over that bucket's latencies, computed in `bucketSeries` from `Aggregator.points`), which `latencySVG` draws as the *Latency over time* chart with the same hit/tip hover technique as the requests chart. `HTMLReport.Settings` (`[]Setting`) renders the *Run settings* table and is omitted when empty; `internal/cli/runinfo.go` fills it (`scenarioSettings`/`hitSettings` for what was tested, `runSettings` for the load shape, `environmentSettings` for the build, then Started/Finished from `runAndReport`). **That table must never carry a secret** — reports are emailed — so `safeURL` keeps only scheme/host/path (cuts at `?`, `#` and the first `{{`, drops `user:pw@`), and header values, bodies, identity contents and Kafka credentials are never listed; `TestScenarioSettingsHTTPFlowListsShapeWithoutSecrets` pins that. Known gap: the *Errors* table shows Go's `url.Error` text, which includes the full request URL with its query string. `cli.buildVersion` is a package var set by `NewRootCommand`, so the report can name the build. `assert.go`: `Summary.Evaluate([]Assertion)` checks named metrics (`success_rate`, `rate`, `latency_p95`, `latency_stddev`, ...) against `Assertion`'s condition fields — everything's normalized to `float64` internally (latency metrics as seconds via `.Seconds()`) so `Assertion`/`Failure` don't need per-metric-type fields. `metricValue` resolves the four fixed percentiles from `LatencyStats` directly (so a hand-built `Summary{Latencies: LatencyStats{P95: ...}}` literal — see `assert_test.go` — still works without needing `hist` populated) and falls through to `latencyPercentileMetric`+`percentile(s.hist, ...)` for any other `"latency_p<N>"`; a percentile assertion on a hand-built `Summary` with no `hist` silently evaluates to `0` rather than panicking — documented as a known limitation of that path, not a bug. `AssertionMetrics` only lists the *fixed* metric names (percentiles are open-ended, so can't be enumerated) — `cli.assertionsFrom` validates a YAML `metric:` name via `report.IsKnownAssertionMetric`, not a plain `slices.Contains(AssertionMetrics, ...)`, or every non-fixed percentile would be rejected. `ParseThreshold`/`IsLatencyMetric` are what let `cli` parse a YAML threshold string ("500ms" vs "0.95") without knowing the unit itself; both also recognize the `latency_p<N>` pattern via `latencyPercentileMetric`. **Fixed percentiles are p50/p75/p90/p95/p99** (`LatencyStats`, the text `Print` line, the HTML table, JSON, and the `latency_p75`-style assertion names — keep all of those in step when adding one; any other `latency_p<N>` is answered from the histogram, and a test pins that the fixed field equals `percentile(hist, N)` exactly). **The HTML report is deliberately script-free** (`TestWriteHTMLProducesSelfContainedPage` forbids `<script`): the *Requests over time* chart's hover is pure CSS — each bucket gets a transparent full-column `.hit` rect **immediately followed by** its `.tip` group, and the stylesheet shows it with `.hit:hover + .tip`. Two ordering rules make that work and are each pinned by a test (and mutation-checked): the hit/tip pairs must be adjacent (a `+` selector fails if anything sits between them), and they must be emitted *after* all the bars (SVG paints in document order, so a bar drawn later would cover a tooltip). The tooltip flips to the left of its column near the right edge, the last x label is right-aligned so it isn't clipped, and bucket width is **not always 1s** — `bucketSeries` makes ~120 buckets for runs over 120s — so the tooltip's rate is `requests / bucketWidth` and the chart says `each bar = Ns`. Y steps come from the 1-2-5 sequence (`niceStep`), so a max of 97 gives 0/50/100. To check chart changes visually, render sample reports to HTML and screenshot them with headless Chrome (`--headless=new --screenshot`); a static screenshot can't hover, so force a tooltip with an injected `svg.chart > g.tip:nth-of-type(N){opacity:1}`.
  - `Assertion` covers a full condition set, not just gte/lte (`Min`/`Max`): `GT`/`LT` (strict, unlike `Min`/`Max`'s inclusive bound), `Is` (exact equality), `In` (membership), and two field-pairs — `Around`+`AroundMargin` (absolute margin) and `DeviatesAround`+`DeviatesPercent` (percentage-of-target margin, so `DeviatesPercent` is *always* a plain percentage like `10`, never duration-parsed even for a `latency_*` metric) — each pair has an `*Exclusive bool` to switch from the default inclusive bound to exclusive. All set condition fields on one `Assertion` combine with AND (`Assertion.violated`); `Assertion.describe()` renders every set condition as a human string regardless of pass/fail, reused both by a failing `Failure.String()` (via `Evaluate`, which only calls `describe()` when `violated` is true) and by `html.go`'s `assertionResults` for a *passing* assertion's report detail — this dual use is why `describe()` doesn't take `actual` as a parameter, only `Assertion` itself. `Failure` dropped its old direct `Min`/`Max` fields in favor of `Reasons []string` (one entry per condition, same pattern as `doHTTP`'s combined check-failure message) — a real API shape change (this is still alpha), so `Failure{Min: ..., Max: ...}` struct literals no longer compile; build a `Failure` from `Assertion.describe()` instead (see `assert_test.go`). `cli.assertionFrom` (singular; called per-entry from `assertionsFrom`) is what rejects a YAML `around` without `around_margin` (or vice versa) — same "both or neither" contract as `deviates_around`/`deviates_percent` — as a config error rather than letting the pair silently no-op (an `Assertion` with only `Around` set and `AroundMargin` nil is inert by construction in `violated`, which is fine for the Go API's `Min`-without-`Max`-style partial use elsewhere, but confusing left silent for a clearly-paired YAML field name).
  - **Per-step breakdown** (`steps.go`): `Aggregator.steps` (a `stepAgg` per `Result.Step`, same bookkeeping as the run: a transport error is a request and a failure but records no latency, each step has its own HDR histogram so it can answer arbitrary percentiles) surfaced as `Summary.Steps []StepSummary` in the *scenario's* order — `engine.Run` passes the generator's `StepNames()` to `Aggregator.SetStepOrder` (first-seen order is arbitrary for round-robin targets under concurrency, and the smoke test showed `missing` listed before `home`); steps that never made a request are omitted, unexpected ones go last. `Print` and the HTML *Steps* table only show it with **two or more** steps (one just repeats the totals); the JSON always has `steps` when any request was named. `Assertion.Step` scopes a metric to a step via `metricSet` — the run and a `StepSummary` both reduce to the same struct, so `latency_p95` means exactly one thing for both. A step that recorded no requests *fails* its assertion (`Failure.Reasons` lists the steps that did run) rather than passing vacuously; an unknown metric is still an error even if the step is also missing. `Failure.Step`/`assertionLabel` render `metric{step=name}`, and `html.go`'s pass/fail matching is keyed by that label (it used to key on `Metric` alone, which would have shown a passing step's assertion as failed). `ValidateSteps` (shared by `cli` and the DSL) rejects an unknown step name before the run. `Summary.Aborted` is the failed assertion that stopped the run early.
  - **`resonate compare`** (`report/compare.go`, `cli/compare.go`): `ReadSummary` decodes a `PrintJSON` report (the unexported `hist` doesn't survive, so only the *fixed* percentiles can be compared — `ParseGate` rejects `latency_p99.9`). A `Gate` is `<metric><op><threshold>` over the change baseline→current: a `%` threshold is relative, otherwise absolute in the metric's unit (a duration for latency, a plain number otherwise); `step:metric` gates one step. Deliberate choices: a gate that can't be evaluated (step missing from either run, unknown metric) is an **error, never a pass**; a *relative* gate on a zero baseline **fails** with a note (0→0.1 errors is not "no change"); the change is rounded to 1e-9 before comparing because latencies are float seconds and 110ms-vs-100ms came out as +9.999999999999998%, landing on the wrong side of `>=` (`TestGateCheck` caught it). Without `--fail-on` it only prints and exits 0. It warns on stderr when either run was aborted.
- **`internal/config`** — YAML scenario schema (`Scenario`/`LoadConfig`/`StageConfig`/`HTTPConfig`/`HTTPTargetConfig`) and `Load`. `HTTPTargetConfig` is reused for `targets`, `flow`, and `setup` entries.
- **`internal/cli`** — Cobra commands, built via `NewRootCommand(version) *cobra.Command` (split out from `Execute` so `cmd/gendocs` can build the tree without running it — see below). `hit.go` (the `resonate hit` command) and `run.go` both build `engine.Options` and a `generator.Generator` then call `runAndReport(a, opts, runOpts{...})` (`common.go`). `runOpts` bundles JSON/Quiet/DryRun/Assertions/ResultsFile so that signature doesn't keep growing positionally. `runAndReport` composes zero or more `func(generator.Result)` callbacks into a single `engine.Options.OnResult` — the progress printer (unless `Quiet`) and `resultsWriter` (if `ResultsFile` is set) both hook in this way rather than each owning `OnResult` outright. `resultsWriter` writes one JSON object per `generator.Result` (JSON Lines) as they complete, relying on the fact `OnResult` is only ever called from `engine.Run`'s single result-consuming goroutine (no locking needed); `Close()` (called explicitly after `engine.Run` returns, not deferred, so its error can propagate) flushes the buffer. `runAndReport` also runs the post-run concurrency-shortfall check (`concurrencyWarning`, stderr-only so `--json` on stdout stays parseable, and skipped when `MaxWorkers>0` since `Summary.Saturated` already covers that case with live-tracked data), owns `parseHeaders`/`parseQuery`, and wires `progressPrinter` (a 1s-ticker goroutine, TTY-detected via `golang.org/x/term` to choose `\r`-overwrite vs. one-line-per-tick). `--dry-run` short-circuits to `dryRun`, which calls `a.Do(ctx, 0)` directly and prints the raw result(s) instead of running the engine at all. `run.go`'s `assertionsFrom` converts `[]config.AssertionConfig` to `[]report.Assertion` — this is where an unknown metric name or a threshold with no condition set gets rejected, *before* the run starts (`report.Evaluate` itself only errors on a metric name, which `assertionsFrom` has already validated, so that path is effectively unreachable from the CLI — it's there because `report` is usable standalone). `checkAssertions` runs after the summary is printed either way, so failing assertions don't hide the results; it returns a non-nil error precisely to give `resonate run scenario.yaml`/`resonate hit ...` a non-zero exit code for CI gating. `resonate hit` gets the same capability via `common.go`'s `parseAssertions`/`parseAssertExpr`, which parses a repeatable `--assert 'metric<op>threshold'` flag (operators `>=`/`<=`/`==`/`>`/`<`, mapped to `Assertion.Min`/`Max`/`Is`/`GT`/`LT` respectively — checked longest-symbol-first in `assertOperators` so `">="` is never mis-split as `">"` + `"=0.95"`) into the exact same `[]report.Assertion` shape `run.go`'s `assertionsFrom` produces from YAML — `runOpts.Assertions`/`checkAssertions` were already generic across both commands (only `hit.go` never populated them before this), so wiring this up needed zero changes to the shared plumbing. `--assert` intentionally only covers the five operators that fit a single `metric op value` expression — `in`/`around`/`deviatesAround` (which need a list or a pair of values) stay scenario-YAML-only, where `config.AssertionConfig`'s named fields have room for them.
- **`cmd/gendocs`** — regenerates `docs/cli/*.md` from `cli.NewRootCommand("dev")` via `cobra/doc`, recursively setting `DisableAutoGenTag` on every command so output is byte-identical across regenerations (no date footer) — that determinism is what makes `make docs-check` (`git status --porcelain -- docs/cli` after regenerating) a meaningful CI gate instead of always showing a diff.

**Validation philosophy** (see `docs/usage.md`'s "Validation" section for the full list): fail fast at construction, before any request is sent, whenever a bad config would otherwise degrade into either silent no-op behavior or — worse — an unthrottled busy loop. Concretely: `generator.validateLiteralURL` rejects non-templated URLs that don't parse as absolute `scheme://host` *at generator construction*, because a URL that fails to parse resolves with zero network I/O, so with no `--rate` set the worker loop would otherwise free-spin at millions of iterations/sec instead of erroring immediately (this was a real, reproduced bug — 10.8M "requests" in 10s at 340% CPU). Templated URLs can't be validated this way (value unknown until render time) and are left to fail per-request instead. `HTTPOptions.BaseURL` is resolved by `resolveBaseURL(base, rawURL)` — called first thing inside `compileHTTPFields`, before `validateLiteralURL` — so a relative (`/`-prefixed) URL with no `BaseURL` configured falls straight through to the exact same fail-fast check an absolute-but-malformed URL would hit, with no extra validation code needed for that case. `resolveBaseURL` only touches URLs starting with `/`: an already-absolute URL, or a template expression (which starts with `{{`, never `/`), passes through untouched, so there's no ambiguity about which URLs `BaseURL` applies to. `compileHTTPFields`'s `baseURL` parameter is threaded through both call sites — `NewHTTPGenerator`'s `targets` loop (`opts.BaseURL`) and `flow.go`'s `compileSteps`/`compileStep` (`opts.HTTP.BaseURL`, threaded through the `Repeat`/`During`/`If` recursion too, so a relative URL inside a nested control-flow block resolves the same way a top-level one does).

**Rules that hold for every protocol** (each was learned from a real bug; `docs/architecture.md` has the short version):
- *Anything that can fail instantly with zero network I/O must be validated at construction or bounded*, because a worker with no `--rate` then spins at millions of iterations/sec. That is `validateLiteralURL`, HTTP/3's `requireHTTPSForHTTP3`, gRPC's `grpc.WaitForReady(true)` (verified: without it a call against a dead server returns in ~14µs), and the "still open at `timeout` is a failure" rule for streams with no `events`/`duration`/`receive`.
- *A call or stream cut off by the run's own end is dropped, not reported* — `runEnded(ctx)` in `grpc.go`, used by gRPC and SSE. It must check `ctx.Err()` **and** the deadline against the clock: gRPC fails a call the instant `time.Until(deadline) <= 0`, microseconds before the context's timer marks it done, so `ctx.Err() != nil` alone let a burst of ~one-per-worker 0ms `DeadlineExceeded` results through at the end of every ramped run. (Plain HTTP/flow requests still report a few end-of-run `context deadline exceeded` errors — pre-existing, and changing it would alter existing behavior.)
- *Streams are reported by their parts* (WS, SSE, gRPC streaming): a connect/open `Result` plus one per message/event, latency = gap since the previous one, `requests` therefore counts messages. Results are only returned when the stream ends, so memory grows with messages per stream — hence the bounds above.
- *Opt-in transports never fall back* (HTTP/3): tests must assert what the **server** observed, not just that the call succeeded.
- *`resonate hit` exits 0 even when every request fails* unless `--assert` is given, so a script that waits for a server with `hit ... && break` quits immediately; probe with `curl` or give it an assertion.

**Docs and example conventions.** `docs/` is the source of truth; each protocol with depth has **one** guide (`grpc.md`, `sse.md`, `http3.md`) and `scenarios.md` just points to it — don't duplicate. Every complete scenario in a guide is tested: the example server's `docs_test.go`/`main_test.go` (or `internal/cli/sse_test.go`) extracts the ```yaml blocks, strict-decodes them with `KnownFields(true)` (because `config.Load` itself silently ignores unknown keys, so a doc typo like `recieve:` would otherwise pass), and runs them through the real `cli.NewRootCommand` against the example server with only the host rewritten. Full scenarios in a guide therefore must target the example server's real endpoints; a long-running illustration is exempted from *running* (not from parsing) by an invisible `<!-- docs-test: parse-only -->` line above the fence. Example servers: stdlib or dynamic-message only (no codegen), `call`/`done` access-style logging, `-log-requests=false` + a periodic summary for load tests (per-request logging dominated the go-grpc-example server's cost), credentials never logged, and a default port that avoids 8080 (a demo that dies with "address already in use" on first run is a bad demo). Shipping a new example server means: a `make example-<proto>-server` target, a guide section, a test that runs the shipped examples and the guide against it, and a line in `docs/architecture.md`'s table.

**Adding a protocol:** generator → facade alias in root `generator.go` → config struct + a link in the `allOf` protocol chain and a `$defs` entry in `scenario.schema.json` (the chain is generated from the list of protocols; extend the list, don't hand-edit nested `if/else`) → `buildGenerator` case in `run.go` (and the protocol list in the unsupported-protocol error) → tests at every layer → guide + sidebar + cross-links → this file. The JSON Schema has no automated test; validate it with a real validator (draft 2020-12) against every `examples/*.yaml` and every full scenario in `docs/`, plus negative cases (a protocol with the wrong section, a typo'd key).

**Protobuf over HTTP** (`internal/generator/http_proto.go`): `HTTPTarget.Proto`/`FlowStep.Proto` (`*ProtoBody`, YAML `proto:`) attach a `protoCodec` to `httpFields` (`withProto`, applied after `compileHTTPFields` so its signature didn't grow). `buildRequest` renders the body template as protobuf JSON and `proto.Marshal`s it (`BytesOut` is the encoded size; Content-Type/Accept default to `application/x-protobuf` unless set); `doHTTP` decodes the reply to protobuf JSON, when a `response` type is set, *before* `expect_body`/`extract` run. The schema loaders (`loadProtoSources`/`loadDescriptorSet`) and `unmarshalGRPCMessage` are shared with gRPC; there is no reflection source (no server to ask). Mutually exclusive with `raw_body`. Not yet in the fluent builder (`Scenario`) — use `HTTPTarget`/`FlowStep` literals with `resonate.ProtoBody`.

**Response compression** (`internal/generator/http_encoding.go`): Go's transport only auto-decompresses gzip when the request has no `Accept-Encoding` of its own (it then sets `resp.Uncompressed`). `doHTTP` calls `decodeResponseBody`, which is a no-op in that case and otherwise decodes `gzip`/`deflate` (zlib, sniffing raw)/`br`/`zstd` by `Content-Encoding`, last coding first. `BytesIn` and `max_response_body` count *decoded* bytes. A decode/read failure while decoding fails the request regardless of `expect_*` (a corrupt payload mustn't pass because nothing inspected it); an *unknown* coding is fatal only when `expect_body`/`extract` need the body. The transport is deliberately untouched (no `DisableCompression`), so SSE keeps Go's behaviour and does **not** decode a self-set `Accept-Encoding`. 

**Request compression** (`compress:` → `HTTPTarget`/`FlowStep`/`SSETarget.Compress`, `withCompress` in `http.go`, `compressRequestBody` in `http_encoding.go`): applied in `buildRequest` *after* `proto` encoding (`encodeBody`), setting `Content-Encoding` unless the target set one. `withCompress` must run after `withProto`: a `{{ }}`-free body (`bodyIsStatic`) is encoded+compressed once there into `staticBody` (so a bad static body fails at construction); templated bodies compress per request. `BytesOut` is the compressed size; an empty body is left empty; mutually exclusive with `raw_body` (sent as given). zstd uses one shared `Encoder.EncodeAll` (concurrency-safe); `deflate` is zlib-wrapped.

### Multiple scenarios

*Added after the rest of this page was written; the notes below are what is non-obvious about it.* User-facing behavior is in [Multiple Scenarios](multiple-scenarios.md).

- **One engine run per scenario, not a new engine.** `engine.RunMulti` (`internal/engine/multi.go`) calls the existing `Run` once per `Spec` in its own goroutine, so every execution model (closed, open, staged, per-VU iterations) works per scenario with no scheduling code of its own. `StartAfter` is a timer raced against `ctx.Done()` before `Run`; it is deliberately outside the scenario's own `Duration`, so `Summary.Duration` of a scenario is its own run while the combined one is the whole wall clock. A scenario cancelled before it starts returns an empty `Summary` and is still listed.
- **The combined `Summary` is built by a second `Aggregator`, not by merging summaries.** `Summary` carries only precomputed numbers (and an unexported histogram), so merging percentiles from summaries would be wrong. Each scenario's `OnResult` feeds the shared `Aggregator` under one mutex; that same mutex serializes the caller's `MultiOptions.OnResult`, because `progressPrinter`/`resultsWriter` assume a single goroutine (`engine.Run` guarantees that per run, and `RunMulti` must restore it across runs). Step order is the union of the generators' `StepNames()`; steps sharing a label merge, which is also how a step repeated in a `repeat` block is reported. `Saturated` is OR'd; `PeakConcurrency` is not combined (a combined peak isn't tracked, and the sum of per-scenario peaks would be an overstatement).
- **Abort.** A scenario's `Options.AbortOn` rules see that scenario alone. On a trip `runSpec` cancels the shared context, which stops every scenario, and prefixes the reason with the scenario name. A run-wide abort rule is rejected (CLI and `Suite`) because evaluating it live would need the combined aggregator snapshotted from several goroutines; judging it at the end is what the existing rules already do. The scoped rules are handed to the engine with `Scenario` cleared, since inside one scenario's run the `Summary` has no `Scenarios` to look the name up in.
- **Assertions are scoped by `Assertion.Scenario`** and resolved inside `Summary.assertionValue` (so the library, `Suite`, and the CLI share it): find the scenario's `Summary`, then apply the usual step logic to it. A missing scenario fails the assertion (like a step that made no requests) rather than passing vacuously; `EvaluatePartial` skips it. `assertionLabel` includes the scenario, and the HTML report matches pass/fail by that label, which is why a same-named assertion for two scenarios doesn't collide (`TestWriteHTMLListsScenariosAndStaysScriptFree` is mutation-checked against exactly that). `ValidateScopedSteps` checks a step against the scenario it is scoped to, using `engine.StepLookup`.
- **Config merge happens on YAML nodes.** `mergeSection` encodes the shared section struct to a node (every field, zeros included), sets the scenario's own keys over it (`setKey`), and strict-decodes the result into the scenario's section. A struct-level merge can't distinguish "scenario set `insecure: false`" from "scenario said nothing", so an override with a zero value would silently lose to a non-zero shared one (`TestResolveScenarioCanOverrideWithZeroValue`). `ScenarioSet.UnmarshalYAML` walks the mapping node by hand to keep file order (a Go map would lose it, and reports list scenarios in file order) and to reject unknown keys inside a scenario. `Node.Decode` does **not** inherit the caller's `KnownFields`, so `decodeStrict` marshals the node and decodes it with a fresh strict decoder. `Load` additionally re-decodes the whole file strictly when `scenarios:` is present, so a typo in a *shared* section or an assertion also fails — single-scenario files keep their old lenient behavior on purpose (changing it would break existing files).
- **Validation order in `runMultiFile`:** resolve (config errors → exit 2) → assertion-scope checks → build every generator (errors name the scenario; earlier generators are closed) → `ValidateScopedSteps` → `ValidateMulti` → run. Nothing is sent until all of that passes (`TestRunScenariosRejectsBadFilesBeforeSendingAnything` asserts zero requests for every bad file). Generators are closed by a `defer` in `runMultiFile`, including on assertion failure (`TestRunScenariosClosesEveryGenerator` checks the server sees the connections close).
- **Reports.** `report.json` gains `scenarios` (`ScenarioSummary` embeds `Summary`, so each entry has the top level's fields flat, plus `name`/`start_after`) — additive, so `schema_version` stays 1 and single-scenario output has no `scenarios` key. `results.jsonl` gains `scenario` (omitted when empty). The Run settings table prefixes each scenario's rows with its name and still lists nothing secret.
- **JSON Schema.** The top level is conditional on `scenarios`: with it, `load` must be absent and the shared sections validate against the `*Partial` defs (nothing required, since shared defaults legitimately lack `targets`/`url`); without it, the original strict defs and protocol chain apply unchanged. The `*Partial` defs are copies of the strict ones' `properties`, so `TestSchemaPartialSectionsMirrorStrictOnes` fails if one drifts. The merged result of a scenario is checked when the scenario is built, not by the schema.
- **`Suite` (`dsl_suite.go`).** Mirrors the YAML: `Scenario.Assert` calls are scoped to that scenario, `Suite.Assert` is run-wide unless `Scenario` is set. `Scenario.Run` was split into `prepare()` (build + validate + abort rules) and `evaluateAssertions`, which `Suite.Run` reuses, so the two can't drift. The suite owns and closes the generators it builds.
- **`Suite.Defaults` / `AddWith` (shared defaults for the builder).** A `Scenario` is stateful, so a default applied *after* a scenario was built would overwrite what the scenario set. `AddWith` therefore stores a build *function*, and `Suite.materialize` creates a fresh `Scenario` per `Run`, applies every default in call order (even ones registered after `AddWith`), then runs the scenario's function — so the scenario's own settings win, and a second `Run` starts clean instead of reusing accumulated state. Defaults are rejected if they start a request (`Scenario.hasRequests`): request-level setters like `Header` lazily start an implicit `HTTPTarget`, which would then collide with the scenario's `Step` ("Target and Step are mutually exclusive") with a confusing error far from the cause. Single-valued setters are replaced; `Identity` appends (documented, and pinned by `TestSuiteIdentityAddsToTheDefaultsPool`) — the one place the builder differs from YAML's replace-the-list rule, because the builder has no way to say "replace the pool".
